# Регламент регулярного аудита АрхГейта

Утверждено пользователем 23.11.2026. Рабочая ветка: `test-hab-propose-rules-20261121`.

## Периодичность
- Каждую неделю по понедельникам в 10:00 по Новосибирску (Asia/Novosibirsk): проверка инструкций всех зарегистрированных агентов и их связей.
- В первый понедельник каждого месяца в 10:00 по Новосибирску: расширенный архитектурный аудит вместо обычного еженедельного (без дублирования).
- После создания агента, изменения инструкции или интеграции: внеочередной адресный аудит затронутых агентов по запросу или при доступном механизме запуска; наличие регламента само по себе не создаёт автоматический GitHub-триггер.

## Порядок
1. Прочитать собственную AGENTS.md и этот регламент; получить актуальную карту агентов из корневого README и фактической структуры репозитория. Не считать README исчерпывающим.
2. Зафиксировать ветку, пути и версии проверенных файлов. Выявить новых агентов и изменённые инструкции относительно предыдущего реестра.
3. Проверить внутреннюю непротиворечивость каждого агента, согласованность с Хабом и общими правилами, границы записи, права, владельцев данных, подтверждения, синхронизацию и восстановление после сбоев.
4. Для ежемесячного глубокого аудита дополнительно проверить архитектуру ролей, дублирование полномочий, масштабируемость, устаревшие инструкции, зависимости и технический drift.
5. Классифицировать: подтверждённый конфликт, неоднозначность, дублирование, drift, устаревание, риск. Указывать точные выдержки, обе стороны, последствия, приоритет и минимальное исправление.
6. Сохранить датированный отчёт в ОТЧЁТЫ/ и обновить РЕЕСТР_ПРОВЕРОК.md и собственную память; перечитать записанные файлы.
7. Не изменять инструкции других агентов без отдельного явного разрешения пользователя. После согласованных исправлений повторно проверить затронутые связи.
8. Если нет доступа к GitHub или запись не удалась, прямо сообщить об ограничении, не заявлять о завершённом аудите и не выдумывать результаты.

## Отчётность
Кратко сообщать: охват, новые/закрытые/открытые проблемы, критические риски, ссылки на отчёт и решения, требующие пользователя. Отсутствие изменений не означает отсутствие конфликтов.
